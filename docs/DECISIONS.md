# Decisions

Where the spec ([`SPEC.md`](SPEC.md)) leaves something open, the simplest sensible option is chosen and recorded here. Newest stage last.

## Stage 1 — skeleton

| # | Decision | Why |
|---|---|---|
| D-001 | Flutter **3.47.9 stable** (Dart 3.13), pinned in CI. Lints: `flutter_lints` plus a few strict rules in `analysis_options.yaml`. | Current stable at the time of writing; `flutter_lints` is lighter than `very_good_analysis` and enough for a small team. |
| D-002 | **Flavors:** Dart entry points `lib/main_dev.dart` / `lib/main_prod.dart` on every platform. Android also has Gradle `productFlavors` (`dev` gets the `.dev` ID suffix and the label "Standwise Dev"), so it must be run with `--flavor dev`. iOS/macOS Xcode schemes and separate Windows binaries are added in stage 8 together with the prod Firebase project. | Xcode schemes need a Mac to create and test; until a prod project exists, a second scheme adds nothing. `lib/main.dart` points at dev so plain `flutter run` works. |
| D-003 | **Bundle / application ID:** `com.sonderling.standwise` (placeholder, the spec says to set it during setup). | Change it in `android/app/build.gradle.kts`, `ios/Runner.xcodeproj`, `macos/Runner/Configs/AppInfo.xcconfig` and the macOS entitlements before the first store upload. |
| D-004 | **Firebase options:** `lib/app/firebase/firebase_options_{dev,prod}.dart` are committed placeholders that `flutterfire configure` overwrites. When they are placeholders, or `Firebase.initializeApp` fails, the app starts in a "Firebase is not configured" mode (banner, unconfigured repositories). | CI can build and test every platform without Firebase credentials, and a broken config never crashes on launch. Firebase config values are identifiers, not secrets (spec §10), so the generated dev file is committed. Prod handling is decided in stage 8. |
| D-005 | **OAuth client IDs** come from `--dart-define-from-file=config/dev.json` (git-ignored; template `config/dev.example.json`). | IDs differ per Firebase project and platform; keeping them out of code means no rebuild of code for a new project. The Windows desktop client secret is not confidential by Google's definition but is still kept out of the repo. |
| D-006 | **Windows sign-in** implemented now (stage 1, not 2) in `lib/core/auth/desktop_google_oauth.dart`: system browser + PKCE (S256) + loopback `HttpServer` on `127.0.0.1:<random port>`, then Firebase `signInWithCredential`. Unit-tested with a simulated browser redirect. | The spike needs a real sign-in on Windows to prove Firestore with security rules. |
| D-007 | **Offline cache** explicitly enabled with unlimited cache size on all platforms (`Settings(persistenceEnabled: true)`). | Default on mobile/macOS; setting it explicitly makes Windows behave the same, and the platform check verifies it. |
| D-008 | **Money rounding:** `amount = (rateMinor × minutes + 30) ~/ 60` — integer maths, rounded half up once per entry. Report totals are sums of per-entry amounts. | Matches what a person would compute per line on an invoice; no `double` anywhere. |
| D-009 | **Manual entry with `to == from`** is a 24-hour entry ending the next day (spec: "if to ≤ from, the end is on the next day"; 24 h is still within the limit). | Literal reading of the spec. |
| D-010 | **Generated localization files** (`lib/l10n/app_localizations*.dart`) are git-ignored; `flutter pub get` regenerates them (`generate: true`). | Keeps diffs clean; ARB files are the source. |
| D-011 | **Platform check** (the stage 1 spike) is a dev-flavor-only screen: Settings → Developer → Platform check. It writes `/_platformChecks/{uid}` (rules allow only the caller's own document) and checks sign-in, write, server read, live listener, offline write, cache read and resync. It goes through the repository interfaces like any feature. | Repeatable on every device, and the "Copy report" button produces the text for the results table below. |
| D-012 | All five tabs are visible in stage 1, including **Team**. Role-based hiding arrives with memberships in stage 3. | No roles exist yet. |
| D-013 | Deployment targets: iOS 15.0, macOS 12.0 (Flutter 3.47 defaults); Android `minSdk` from Flutter (≥ 24). | Satisfy current Firebase SDK minimums. |
| D-014 | **License: MIT** (`LICENSE`), changed from proprietary on 2026-11-04 at the owner's request. The repository is meant to become public. | Public repositories get GitHub-hosted Actions runners (including macOS) without a minutes quota. Nothing secret is in the history: the desktop client secret lives only in GitHub secrets and the gitignored `config/dev.json`. |
| D-015 | macOS entitlements: App Sandbox with `network.client` and `keychain-access-groups` (`$(AppIdentifierPrefix)com.sonderling.standwise`). | Required for Google sign-in and Firebase Auth's keychain storage; the group needs a signing team when run locally (docs/SETUP.md). |
| D-016 | **FlutterFire pinned to the 4.x line** (`firebase_core ^4.15`, `firebase_auth ^6`, `cloud_firestore ^6`; Firebase Apple SDK 12.x), not 5.x. | FlutterFire 5.x uses Firebase Apple SDK 13, which needs `gtm-session-fetcher` ≥ 4, while `google_sign_in_ios` (GoogleSignIn-iOS 9) needs 3.x, so iOS/macOS packages can't resolve. Move to 5.x when `google_sign_in_ios` supports GoogleSignIn-iOS 10. |
| D-017 | **Downloadable dev builds from CI** (same approach as the PilotLogbook repo): every push to `main` publishes a `dev-latest` pre-release with `Standwise-dev-windows.zip` and `Standwise-dev.apk`. The APK is signed with one persistent key (GitHub secrets, or generated once and kept in the Actions cache) so updates install over the old version. Google client IDs come from Actions variables `GOOGLE_SERVER_CLIENT_ID`, `GOOGLE_APPLE_CLIENT_ID`, `GOOGLE_DESKTOP_CLIENT_ID` and secret `GOOGLE_DESKTOP_CLIENT_SECRET`. | Lets the owner test on Windows and Android without installing Flutter. Proper versioned releases come in stage 8. |
| D-018 | **`standwise-dev` is live** (project number 655809046065): Blaze, budget alert 22 PLN/month (≈ €5; the billing account is in PLN), Firestore `eur3`, Google sign-in enabled (consent screen External, in production; only `openid email profile`). `firebase_options_dev.dart` is committed. The Google Services Gradle plugin and `google-services.json` are **not** used: FlutterFire reads options from Dart and Android sign-in uses `serverClientId`. macOS shares the iOS Firebase app (same bundle ID). | Fewer moving parts; identifiers only in the repo, the desktop client secret only in GitHub secrets / local `config/dev.json`. Android sign-in still needs the CI signing key's SHA-1/SHA-256 added in Firebase. |
| D-019 | **CI on a public repository:** every pull request runs analyze/test and the Android, Windows, macOS and iOS builds. (Briefly limited to save minutes while the repo was private, 2026-11-04.) Bundle ID `com.sonderling.standwise` (D-003) confirmed by the owner 2026-11-04. | Public repositories have no Actions minutes quota on GitHub-hosted runners. No Mac is available for the macOS spike for now. |
| D-020 | **Membership documents also store `uid`** (in addition to the document ID). `onUserProfileUpdated` finds all memberships of a user with one collection-group query `members where uid == …` (single-field override in `firestore.indexes.json`). | The spec's member fields don't include it, but a collection-group query can't filter on the document ID alone. Functions write memberships, so the field is always correct. |
| D-021 | **Cloud Functions:** TypeScript (ES modules, Node 22) in `functions/`, region **`europe-west1`** (inside the `eur3` multi-region), firebase-functions 7 and firebase-admin 13, input validation with zod. Tests use Node's built-in `node:test`, with TypeScript run directly by Node (type stripping), so there is no extra test runner. Unit tests run without emulators; `npm run test:emulator` covers Firestore logic. | Fewest dependencies. Region next to the data, as close as possible to Polish users. |
| D-022 | **Security rules** cover the whole data model now (spec §3.2, §6), not just stage 2 collections, with emulator tests in `rules-tests/`. Additions where the spec was open: employees can't list members (only their own membership); admins can read timers (who is on the clock) but never write them; projects and entries are never hard-deleted by clients; timer `start` may not be more than 5 minutes in the future; `durationMin` must equal the whole minutes between `start` and `end`. | Later stages build on fixed, tested rules instead of growing them screen by screen. |
| D-023 | **Onboarding redirects** (`lib/app/session.dart`, `sessionRedirect` in the router): loading → welcome (signed out) → "Your name" (no valid first/last name) → organization choice (no membership yet) → app. Without Firebase the app still opens straight into the shell. Profile writes don't block on the server: they return after 5 s if the device is offline, because the local cache already has the name. | One pure, unit-tested function decides every redirect. Works offline after the first sign-in. |
| D-024 | **Emulators in the app:** `--dart-define=USE_EMULATORS=true` (dev flavor only) points Auth and Firestore at the local emulator suite. Not yet tried on a real device. | Lets you test without touching `standwise-dev` data. |
| D-025 | **Android SHA fingerprints** of the CI signing key are printed in the **Build Android** job summary (main and manual runs). They are public certificate hashes, not secrets. | So the owner can add them in Firebase without installing Java tools. |
| D-026 | **Callable functions over plain HTTP** (`lib/data/firebase/callable_client.dart`): `POST {"data": …}` with the user's ID token, reply `{"result": …}` or `{"error": {status, message, details.reason}}`. The function's `details.reason` maps to an app error code, so the app shows a specific message. | The `cloud_functions` plugin has no Windows support; the callable protocol is simple and identical on every platform. |
| D-027 | **Invite codes:** 8 characters `XXXX-XXXX` from an alphabet without look-alikes (no 0/O/1/I/L), random from `crypto`, valid 7 days, single use. Only the SHA-256 hash is stored (`codeHash`); the plain code is shown once to the admin and sent in the email. `acceptInvite` finds the invite with a collection-group query on `codeHash` and checks the invitee's verified email matches. A user may own at most 5 organizations. | A leaked database export can't be used to join. Typing the code works without deep links. |
| D-028 | **Invite emails** are queued as documents in the top-level `mail` collection in the format of the Firebase **Trigger Email** extension (`firestore-send-email`). Until the extension is installed (docs/SETUP.md §8) nothing is sent and the admin shares the code by hand. The email's `standwise://join?code=` link needs deep-link handling, which arrives in stage 8; the code works without it. Member management (role changes, disabling) is stage 7. | No email provider is chosen yet; the extension is replaceable without touching functions. |
| D-029 | **Rates for entries without a project** are stored under the rate key `_none` (`noProjectKey`), and summaries use the same key in `byProject`. | One rate document per (person, project) stays the only model; "No project" is just another key. |
| D-030 | **Local-first writes:** every Firestore write goes through `SyncTracker` (`lib/data/sync.dart`), which counts unconfirmed writes and reads `isFromCache` from the timer listener. The header shows Saved / Saving… / Offline; a rejected write shows a message. `connectivity_plus` is not used. | Firestore already queues writes offline; tracking the writes we made is more accurate than network probes. |
| D-031 | **Monthly summaries** (`orgs/{org}/summaries/{uid}_{YYYY-MM}`) are written by `onEntryWritten`. The day is computed in the organization's timezone and clamped into the entry's `monthKey` month; each bucket stores work/standby minutes, amount and entry `count`. Deleted entries leave the summary; `purgeDeletedEntries` removes soft-deleted entries after 30 days. | Admin reports read ~1 document per person per month instead of every entry. |
| D-032 | **Team view from summaries, CSV from entries:** totals, people table, chart and project table read summaries; one person's entries and the team CSV read the entries themselves. Totals may trail a fresh entry by a few seconds (noted under the table). | Cheap reads for the overview; the export stays exact. |
| D-033 | **Entry editing in a dialog** on every width instead of inline table rows on wide screens. | One editor to test and keep accessible; inline editing can come later. |
| D-034 | **Sample data** (Projects → Load sample data, admins): three projects named `Sample: …` with the admin's rates and a few days of entries; "Remove sample data" deletes them. | A new organization can see reports without typing hours. |
| D-035 | **Account deletion** keeps tracked hours with the employers, without the person's name or email; the spec's optional "owner deletes their hours too" is not offered. A person who owns an organization must transfer ownership or delete it first. | Employers may need the hours for payroll; one clear path is safer. |
| D-036 | **Saving CSV:** a save dialog via `file_selector` on Windows/macOS, the share sheet via `share_plus` on Android/iOS. Files are UTF-8 with BOM and CRLF; cells starting with `= + - @` are prefixed with `'`. | Excel opens the file correctly; formula injection is defused. |
| D-037 | **Emulator tests run one file at a time** (`--test-concurrency=1`). | The files share one emulator and clear data between tests. |
| D-038 | **TestFlight from CI without a Mac** (`.github/workflows/apple.yml`, `tool/apple/`): every push to `main` builds the dev app for iOS and macOS, signs it and uploads it to TestFlight. An App Store Connect API key (role App Manager, secrets `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_KEY`) registers the App ID, creates a temporary Apple Distribution certificate (plus a Mac Installer certificate for macOS) and an App Store profile per run, and revokes them at the end; uploaded builds stay valid. The Xcode projects keep automatic signing; CI switches the app target to manual signing. Build number = workflow run number. macOS ships through the Mac App Store/TestFlight, not Developer ID. Team ID `867N95XY27`, app "Standwise Time". | The owner has an Apple Developer account but no Mac; no certificate or password has to be stored. |
| D-039 | **Google sign-in URL scheme** (reversed iOS client ID of `standwise-dev`) is in both `Info.plist` files; `ITSAppUsesNonExemptEncryption = NO` skips the export-compliance question; macOS category Productivity. The prod client ID replaces the scheme in stage 8. | Required by GoogleSignIn on iOS/macOS and by App Store Connect. |
| D-040 | **Team CSV = the People table** (owner's request 2026-11-09): "Export team CSV" saves one row per person (everyone active, zeros included, plus former members with hours) with Work, Standby, Total (h:mm), Hours (decimal), Entries, Amount and a Total row, computed from the entries in the range and project filter. "Export all entries" keeps the detailed per-entry team CSV (D-032). | The owner uses the export for the combined calculation per person. |
| D-041 | **App icon, legal pages, no source link** (owner's request 2026-11-09): the icon is the "split ring" (picked by the owner from five variants): a green work arc and an amber standby arc around white clock hands on a dark navy gradient; it is drawn by `tool/icon/make_icon.py` and spread to Android (adaptive), iOS, macOS and Windows by `flutter_launcher_icons`. `docs/PRIVACY.md` and `docs/TERMS.md` are bundled as assets and shown in the app (Welcome and Settings → About) by a small Markdown renderer, so they open offline; the app never sends users to GitHub or the web for them (owner's request); their GitHub URLs (`Brand.privacyPolicyUrl`, `Brand.termsUrl`) are only for the store listings. Operator: Pavlo Yavorskyi Video Grill FPV, Szczecin. The "Source code" item from spec §5.7 is removed from About. | Spec §11 icon idea; stores need a public policy URL and the app must show it before sign-in. Owner asked to drop the source link. |
| D-042 | **TestFlight on demand, not on every push** (2026-11-09): `apple.yml` runs on `workflow_dispatch` and `v*` tags only. Supersedes the "every push to `main`" part of D-038; the temporary-certificate approach stays. | Each run revokes its temporary Apple Distribution (and Mac Installer) certificates, and Apple emails the owner about every revoke ("null null has revoked your certificate"). Fewer runs, fewer emails; nobody needs a TestFlight build per commit. |
| D-043 | **Join invitations without the code** (owner's request 2026-11-09): callable `listMyInvites` returns pending, unexpired invites for the caller's verified email (collection-group query on `invites.email`, index override added) with organization and inviter name; `acceptInvite` takes either `{code}` or `{orgId, inviteId}`. The organization screen shows "Invitations for you" with a Join button; the code card stays. The invite email says to sign in with the invited address and tap Join; the code is the fallback. Emails still go through the Trigger Email extension (SETUP §8, Gmail app password is enough). | The verified Google email is the same proof the code-based path already required, so the code adds nothing for the invited account; typing it was the main friction. |
| D-044 | **Timer: project required and remembered; Team: a row per person and project** (owner's request 2026-11-09): the Timer screen drops the week chart (it stays in My reports) and puts the project picker before the description. "No project" is no longer offered for new or edited entries, and Start, Add and Save stay disabled until a project is chosen (`TimerActions` also refuses with `projectRequired`); old entries without a project still show and count. The last mode (Timer/Manual) and, per organization, the last project are remembered on the device (`shared_preferences`); without a remembered project the latest entry's active project, then the first active project, is preselected. The Team people table and the team summary CSV show one row per person and project (a person without hours once, with "—"), with Project, Work rate and Standby rate columns; the rates are the member's current ones (admins may read them). Invite emails are sent from `infostandwise@gmail.com` (SETUP §8). | Hours and amounts only make sense with a project and rate; an employee working on two projects at different rates needs two rows to be checked. Remembering the choices saves taps for people who track the same project every day. |
| D-045 | **Own mail sender instead of the Trigger Email extension** (2026-11-09): Firebase Extensions shut down on 31 March 2027, so `sendMail` (`functions/src/mail/send_mail.ts`, Firestore trigger on `mail/{id}`) sends the queued documents itself with nodemailer over Gmail SMTP as `infostandwise@gmail.com` (owner's choice). The Gmail app password is the Secret Manager secret `SMTP_PASSWORD`. Each document is sent once; `delivery` records SUCCESS or ERROR, and after a successful send the message body (with the invite code) is deleted. Supersedes the extension part of D-028; the `mail` document format is unchanged. To stay out of spam the email has no `standwise://` link (filters distrust custom schemes) and sets Reply-To; reliable inbox delivery needs an own domain with SPF/DKIM (planned before launch). | Extensions can't be installed after March 2027; a 60-line function has no extra moving parts and keeps codes out of Firestore once sent. |
